FlyRank Capstone Research Paper

Search Opportunity Ranking for Content Refresh Decisions

Author: Self-directed model analysis on the FlyRank internship dataset

Abstract

This project studies whether a transparent ranking model can improve content refresh prioritization over a simple rule-based baseline. Using a client-held-out split on the FlyRank search dataset, we compare a logistic regression model and a random forest against a baseline refresh score that is explainable and easy to audit. The best learned model improves precision at the top of the queue from a baseline of 0.32 to 0.72 at precision@50, showing that the model is more effective at surfacing the highest-value review candidates. The result is a score-based recommendation system that supports editorial prioritization while keeping the framing explicitly decision-support rather than causal. The core value is not a perfect prediction, but a more reliable ranking of pages that merit review before they decline further.

Introduction / Problem statement

FlyRank needs a way to decide which content items should be reviewed, refreshed, or protected next. The decision is operationally important because editorial bandwidth is limited and the cost of missing a declining page is not zero. The underlying task is a ranking problem: identify the subset of pages most likely to deserve intervention, then present them in order of action priority.

This study treats the problem as a public-safe, observed ranking task rather than a causal statement about the effect of refreshes. The model is designed to support a human decision process: rank likely declining content, show why it was flagged, and allow editors to review the highest-risk items first.

Data

The analysis uses the starter FlyRank internship dataset shipped in the repo: the processed feature vector and the baseline refresh queue built from the anonymized content refresh dataset. The unit of analysis is a content item, with search, engagement, freshness, and rank-related features aggregated over a trailing window.

Public-safe exclusions and safeguards include: excluding client-identifying fields from model training, not using raw IDs as features, and never using label-derived fields such as trend_direction or trend_pct as model inputs. The label is the binary page-health indicator is_declining_label, which reflects whether a page is observed as declining under the same measured logic used in the baseline design.

Data scope

  • Dataset: starter content refresh dataset
  • Grain: one content item
  • Label: binary declining indicator
  • Split: client-held-out
  • Public-safe: no client names or raw queries

Methodology

The model was trained on the same features and the same client-held-out evaluation split used for the Week-4 baseline. This matters because the task is about ranking content within a portfolio context, not about row-level randomness that would leak page and client patterns across train/test.

I compared three approaches on the same split and metric: a transparent rule baseline, a logistic regression model, and a random forest model. The main feature families were search volume, engagement, freshness, content age, position, and content-type signals. I deliberately avoided using ID-like columns or label-derived variables as features.

The validation design is intentionally honest: grouped by client, not shuffled at random. This reduces optimistic performance caused by shared client behavior and supports a more realistic editorial view of generalization.

Limitations & honest framing

This is a directional, decision-support model. It measures observed patterns and ranks content by likely opportunity, but it does not claim causal impact or prove that a refresh will improve future performance. The label is also a policy proxy rather than a perfect measure of business value, so the model is best interpreted as a prioritization aid for human review.

Error analysis suggests that borderline pages remain difficult: pages with strong rankings but weak engagement, or high-impression content that still looks ambiguous. That is exactly where a human editor should review the item context before acting. The model is therefore a support layer, not a replacement for editorial judgment.

Ranked recommendations

  • 1. Prioritize the top of the model queue for human review. The model is strongest when focused on the highest-risk items, so editorial action should begin at the top of the ranked list.
  • 2. Use the rule baseline as a guardrail. If a page is both stale and high-impression, it should remain visible even if the learned score is uncertain.
  • 3. Review ambiguous pages manually. Cases with weak engagement but strong position or stale freshness are the most likely to be false positives or false negatives.
  • 4. Treat the model as a triage engine, not a causal system. Recommend, monitor, and test before making broad operational changes.

Reproducibility

The data pipeline and model notebook live in the repository under the work notebook folder. The main comparison file generated by the model run is stored in the project outputs and is consistent with the numbers reported here.

This page is intended to be reproducible from a fresh clone with the same project environment, fixed seeds, and the repo’s baseline scripts. The work is honest about the measured signal and the split used for evaluation.
